## A. 依赖与环境类

### A1. HuggingFace Xet 下载通道 401
- **现象**：`snapshot_download` 走 xet 协议时报 `HTTP 401 Unauthorized (cas-server.xethub.hf.co)`。
- **根因**：新版 huggingface_hub 默认启用 Xet 内容寻址下载，在代理/加速网络下鉴权失败。
- **修复**：`HF_HUB_DISABLE_XET=1` 回退传统 HTTP 通道，断点续传完成。
- **建议**：下载工具封装里默认带 `HF_HUB_DISABLE_XET` 兜底重试；模型下载后加完整性校验（safetensors 头解析 + tensor 计数，本次是手工验证的，应进 `prepare` 脚本）。

### A2. datasets 与 pyarrow 不兼容
- **现象**：`prepare_gsm8k.py` 一行跑不了：`AttributeError: module 'pyarrow' has no attribute 'PyExtensionType'`。
- **根因**：环境里同时装了旧版 datasets（还在用 `pa.PyExtensionType`）和新版 pyarrow（已删除该符号）。依赖矩阵失配。
- **修复**：`uv pip install -U 'datasets>=3.2'` → datasets 5.0.1。
- **建议**：所有关键库的兼容矩阵钉进 lockfile（uv/pip-constraints）；提供 `doctor` 预检命令：`python -c "import torch, verl, vllm, transformers, datasets, pyarrow"` 在训练启动前必跑。

### A3. 升级 datasets 连坐 huggingface_hub
- **现象**：A2 修复后训练启动才炸：`huggingface-hub>=0.34.0,<1.0 is required ... but found huggingface-hub==1.33.0`。
- **根因**：datasets 5.0.1 拉入 hub 1.x，与 transformers 4.57 的 `<1.0` 约束冲突。问题在训练启动时而非安装时暴露，浪费一个 attempt。
- **修复**：钉 `huggingface-hub==0.35.3`。
- **建议**：同 A2 的 lockfile 方案；且 `run_grpo.sh` 启动前应先做 A2 的 import 冒烟检查（本次这类问题烧掉了约 40 分钟的试错）。

### A4. flash_attn：verl 的硬依赖 + 无可用安装途径（本次最大的坑）
- **现象**（三层连环）：
  1. verl `utils/attention_utils.py` 在 CUDA 上**无回退**地 `from flash_attn.bert_padding import ...`（NPU 反而有回退）——而它需要的只是 4 个纯 torch 的 padding 工具函数；
  2. flash-attn 官方 release 没有 torch2.9+cp310 的 wheel（只有 cp312）；torch2.8+cp310 wheel 装上后 `undefined symbol: _ZNK3c106SymInt6sym_neERKS0_`（C++ ABI 不匹配）；本机 nvcc 只有 CUDA 11.8，无法对 torch2.9+cu128 现场编译；
  3. vllm 的 `vllm_flash_attn` 用 try/except 探测 `flash_attn.cute.interface`（FA4 检测），但残留的坏 wheel 使 import 抛 **AttributeError**（不被 except ImportError 捕获）→ vllm 初始化崩。
- **修复**：卸干净 wheel 残留；手写最小 shim 包 `flash_attn/`（`bert_padding.py` 纯 torch 移植，语义对齐上游——注意上游 `unpad_input` 第一个返回值是 `index_first_axis` 压缩后的张量，不是原张量）；不提供 CE shim，让 verl `FLAH_ATTN_CROSS_ENTROPY_LOSS_AVAILABLE=False` 走 `logprobs_from_logits_v2` torch 回退（提供 CE shim 反而触发 verl 断言：要求返回 `(losses, z_losses)` 元组，标量 loss 导致 `view(*batch_dim)` "size 1 vs 2072" 崩溃）。
- **建议**（对 verl 源码）：
  - `bert_padding` 的 4 个函数就是几十行纯 torch，应该 vendor 进 verl，而不是为了 padding 工具强制用户装一个数 GB 的 CUDA 扩展；
  - CE 路径（triton cross_entropy）应做成显式 opt-in 而非 import 探测即启用；
  - 顺带：`FLAH_ATTN_CROSS_ENTROPY_LOSS_AVAILABLE` 拼写错误（应为 FLASH）。
  - vllm 侧：FA4 探测的 except 应捕 `Exception` 或至少 `BaseException` 中的 AttributeError 场景。

### A5. verl 默认强制 flash_attention_2
- **现象**：actor 模型加载即抛 `FlashAttention2 has been toggled on, but ... not installed`。
- **根因**：`verl/workers/config/model.py:185` 默认 `attn_implementation="flash_attention_2"`，不探测可用性。
- **修复**：hydra 覆盖 `+actor_rollout_ref.model.override_config.attn_implementation=sdpa`。
- **建议**：默认值应为"探测到的最优实现"（flash_attn 可用则 FA2，否则 sdpa + warning）；至少在配置注释里写明依赖关系。

## B. 脚本与路径类（仓库脚本是 WSL 专属写法）

### B6. supervise_run.sh 硬编码本地工具与路径
- **现象**：`/root/tools/bin/with-lock: No such file or directory`，`$HOME/rheo-a` 路径不存在。
- **修复**：临时写了 flock 版 with-lock + `ln -s /root/rheo /root/rheo-a`。
- **建议**：锁工具缺失时应降级直跑（`command -v with-lock || exec bash ...`）；仓库路径用 `$(cd "$(dirname "$0")/.." && pwd)` 推导，禁止 `$HOME/rheo-a` 这类私人绝对路径进脚本。

### B7. run_grpo.sh 默认 PYTHON 指向本地 venv
- **现象**：`/root/tools/venvs/rheo/bin/python: No such file or directory`，supervisor 空转 2 批。
- **修复**：启动器 export `PYTHON=/root/venv-rheo/bin/python`。
- **建议**：默认 `${PYTHON:-python}`（PATH 语义）；文档要求先 `source venv`。

### B8. rollout util 封顶 0.72 导致每批必失败一次
- **现象**：每批先在 0.72 档吃一次 vLLM `Free memory on device (16.39) < desired (0.72, 16.93)` 拒绝，自动降 0.66 才能起——每批白烧约 5 分钟初始化。
- **根因**：util 在 ray/主进程充分长起来**之前**用 `mem_get_info` 计算，云端这些常驻进程随后再吃 0.5-1GB，0.72 必然过不了 vLLM 启动检查。本地 Windows 桌面占用波动是同一类问题（脚本注释里其实已经意识到了）。
- **修复**：`UTIL_CAP` 环境变量封顶（先 0.66，OOM 后 0.55）。
- **建议**：util 计算移到 ray 初始化之后；或对动态计算值乘一个 0.9 的保守系数；降档梯子里加入 micro batch（见 C10）。

## C. 显存与资源管理类

### C9. 训练步 OOM（micro=8）
- **现象**：`_compute_old_log_prob` 阶段 OOM。
- **修复**：`ppo_micro_batch_size_per_gpu` 8→4。
- **说明**：1.5B 模型 logits 巨大（vocab 152k），micro=8 时激活+logprob 峰值超限。

### C10. LoRA 合并/权重同步 OOM（micro=4 下仍复现，本次最顽固）
- **现象**：训练 29 步都正常（reward 0.61→0.92），然后在 `actor_rollout_update_weights` / `backup_base_model_weights` 处 OOM：`param.data.clone()` 需要 892MB，只剩 735MB。每 5 步的 checkpoint 保存与每步的权重同步共用这条合并路径，保存的额外 gathered state 一叠加就炸。
- **错误修复记录**（避免重复踩）：先把 rollout util 0.66→0.55 **没有用**——vLLM 常驻的 3.5GB 是模型权重本身，与 KV 配额无关。真正有效的是 micro 4→2（actor 峰值 19.3GB→约 17GB），合并期余量 >2GB。
- **建议**（对 verl 源码，价值最高的一条）：
  - `backup_base_model_weights` 用 `param.data.clone().cpu()`——先在 GPU 上克隆完整张量再搬 CPU，峰值 = 整个基础模型。应改为流式 `.to('cpu', copy=True)` 或分块搬移；
  - LoRA 合并也应分块 in-place，不要整模型快照；
  - 运行时加"显存预算器"：vLLM 权重+KV + actor 峰值 + 合并峰值三者的和应可预测并在启动时报错，而不是跑到第 30 步才炸。

### C11. OOM 重试梯子缺少关键杠杆
- **现象**：run_grpo 的 6 次 attempt 重试只降 rollout util，micro batch 不在梯子里，导致同样的 OOM 重试 6 次也过不去（每次还白烧 5-8 分钟初始化）。
- **建议**：自动降档梯子应为：util → micro_batch 减半 → max_num_seqs 减半；并对"重复同一 OOM 签名"快速跳档而不是线性重试。

## D. 磁盘与产物生命周期类

### D12. checkpoint 洪水（两次灌满磁盘的直接原因）
- **现象**：`PytorchStreamWriter failed writing file data/730`、`unexpected pos ... vs ...` 等看似"文件损坏"的报错，实际全是磁盘写满。
- **根因**：三个配置叠加——`save_freq=5` × `lora.merge=true`（每份存合并后 fp32 完整模型 + 优化器状态 = **6.8GB**，而 LoRA 适配器本身只有 ~30MB）× 无保留上限（verl 默认全留）。40 步 ≈ 8 份 ≈ 54GB。且 `CKPT_DIR` 默认 `$HOME/tools`（系统盘）。
- **修复**：CKPT_DIR 迁到数据盘；手工只留最新 checkpoint；清缓存腾出系统盘。
- **建议**：
  - 默认只存 LoRA 适配器（30MB），合并模型按需导出；
  - `trainer.max_ckpt_to_keep=2`；
  - 保存前 stat 磁盘剩余空间，不足时显式报错（见 D13）；
  - CKPT_DIR/日志目录/trace 目录统一走"可配置 scratch 盘"一个变量，不许散落默认值。

### D13. ENOSPC（磁盘满）的错误呈现灾难
- **现象**：磁盘满后，错误以 4 种不相干的面目出现（写坏、引擎起不来、JSON 解码失败、甚至外部工具无法执行），日志里没有任何一条说"磁盘满了"，排障走了大弯路。
- **建议**：引擎应在所有大文件写入路径上捕获 ENOSPC 并输出 `ENOSPC: 需要 X GB，当前 Y GB（路径）`；supervisor 每批开始前 `df` 检查并设阈值告警。

### D14. trace spill 目录生命周期靠人脑管理
- **现象**：`run_grpo.sh` 注释要求"全新跑之前清空 spill 目录，断点续跑保留"，但没有任何机制区分这两种情况。第一轮中止后若直接续跑，merge 会把两轮事件混在一起。
- **修复**：人工判断后清空。
- **建议**：给 spill 事件打 run_id（启动时间戳/uuid），`merge_trace.py` 按 run_id 分段或拒绝混合历史；supervisor 用固定 run_id 管理续跑语义。

## E. 失败处理与可观测性类

### E15. run_grpo 的失败分类器太弱
- **现象**：`unrecognized failure; giving up` 大量出现。依赖缺失（A3/A4）这类**必死**错误也烧满 6 次重试；而"engine init 失败"这类瞬态错误倒是正确重试了。
- **建议**：错误分类——导入/配置/路径类 → 立即终止并高亮根因；OOM/NCCL/引擎启动 → 降档重试。判据就是 log 里的异常签名，值得花半天做一个 matcher 表。

### E16. 验证点丢失
- **现象**：`test_freq=10` 计划 4 次验证（10/20/30/40），第 30 步的验证随那次崩溃丢了，最终曲线只有 3 个点。
- **建议**：验证应在 resume 后立即补跑一次（resume 点 = 上次保存点，天然是 test_freq 的倍数）；或把"验证"与"训练步"解耦为独立阶段。

### E17. 每次重试都完整重启 ray（5-8 分钟/次）
- **现象**：6 次 attempt 的重试粒度太粗，初始化成本反复支付。
- **建议**：同批内的降档重试应复用 ray cluster，只重建 worker；这也是工业引擎省钱（按量计费 GPU）的关键点。

### E18. 进程清理的自匹配陷阱
- **现象**：`pkill -f supervise_run.sh` 会匹配到执行它的 shell 自身（命令行文本包含该串），把启动命令一起杀掉，两次。
- **建议**：脚本用 PID 文件管理生命周期（`/run/rheo-train.pid`），停止走 `kill $(cat pidfile)`；这也是工业化的基本要求。

## F. 其他

### F19. Python 版本三方不一致
- **现象**：云镜像 3.12、实际 venv 3.10（miniconda base）、仓库 `pyproject.toml` 要求 `>=3.11`（导致 `rheotrace` 无法装进 venv）。
- **修复**：`PYTHONPATH=/root/rheo` 让 merge_trace 以本地目录方式 import 到 rheotrace。
- **建议**：统一钉一个版本并在 setup 脚本里 `python -V` 断言；`merge_trace.py` 自行把 REPO_DIR 插入 sys.path（或让 rheotrace 可在 3.10 安装）。

### F20. sitecustomize 引导靠手工拷贝
- **现象**：指南要求 `cp bench/m0/sitecustomize.py $(python -c ...)/sitecustomize.py`——重建 venv 就丢，且容易漏。
- **建议**：改用启动器 export `PYTHONPATH=bench/m0`（sitecustomize 本来就支持从 PYTHONPATH 加载），零拷贝。

### F21. attempt 日志落系统盘且不轮转
- **现象**：每个 attempt 数 MB 日志写 `bench/results/.../logs/`（系统盘），失败重试多时加速磁盘耗尽。
- **建议**：日志与 checkpoint 同走 scratch 盘；按保留 N 份轮转。

### F22. 模型下载无完整性校验
- **现象**：断点续传完成后只能人工确认（本次手工 safetensors 全量加载验证 338 tensor）。
- **建议**：prepare 脚本内置校验步骤（头部解析 + 权重映射比对 + 抽样 tensor 加载）。

## G. 交付物层级的发现（二次复盘补充，2026-09-30 晚）

> 首次复盘后对产物本身做了核查（trace 覆盖、曲线渲染、指标语义），发现以下问题。按重要度排序。

### G1.【最重要】最终轨迹文件只覆盖 step 30-40，不是完整 40 步
- **证据**：`m0-baseline.rheotrace.jsonl` 首个 `weight_sync` 事件 `trainer_step: 30`，首个 `segment_start` 的 `meta.global_steps: 31`；`run_end.summary`：2248 segments / 17 weight_syncs。
- **成因**：首次训练在 step 29 崩溃后，我在重启前按 `run_grpo.sh` 注释的要求清空了 traces-spill 目录（40MB）——当时判断"全新跑"是正确的，但 verl 随后自动从 step 30 checkpoint 续训，导致 1-29 步的轨迹事件随目录一起被删且无法找回。
- **validate ok=True 的盲区**：校验器验证的是结构合法性（schema、块覆盖、版本账本），不校验"轨迹覆盖了计划中的全部 step"。一个只含后半程的轨迹也能全绿。
- **修复选项**：
  1. 接受现状并在交付说明中标注覆盖范围（M0 目标是管线验证，后半程轨迹已含全部事件类型，结构有效）；
  2. 完整重跑 40 步（删 checkpoint + 清 spill，从头 ~1.5-2h，¥4-6）换取完整轨迹。
- **源码优化建议**：
  - spill 目录生命周期由 supervisor 用 run_id 管理，禁止人工 rm 判断（呼应 D14）；
  - `merge_trace.py`/validator 增加**覆盖率断言**：对照训练日志/tensorboard 的 step 集合，缺 step 时至少 WARNING 并在输出头部标注 `covered_steps: 30-40`；
  - 覆盖率信息应写进 `run_start.meta`（如 `resume_from_step: 30`），下游消费方不必反推。

### G2. reward 曲线 PNG 图例遮挡数据区（已修复）
- **现象**：首版图 19 条图例画在坐标轴内部，遮住上面板右侧约 1/3 数据区，train 曲线在 ~step 22 后"消失"（实际被盖住）。
- **修复**：`plot_reward.py` 图例移到轴外（`bbox_to_anchor=(1.01, 1.0)` 双列），画布加宽 8→11 英寸，已重新生成。
- **建议**：绘图脚本应固定"图例在轴外"的布局约定；产物 PNG 应有人眼/自动化审查环节（本次是二次复盘才发现，首次交付声明"完成"时并未看过图）。

### G3. 验证点缺失：计划 4 次（10/20/30/40），实际只有 3 个
- step 30 验证随该次崩溃永久丢失，曲线 val-core 只有 10/20/40 三点。已在 E16 建议恢复后补跑；此处在交付层面再次强调：对"基准曲线"类产物，验证点缺失应显式标注而非默认连贯。

### G4. 曲线由三次续训拼接，科学性论证（保留的结论）
- 拼接构成：step 1-29（micro=4/util=0.66）+ 31-34（util=0.55）+ 36-40（micro=2/util=0.55）；step 5/30/35 有缺口（崩溃边界）。
- **连续性依据**：micro batch 是纯执行参数，不改梯度数学；verl checkpoint 保存并恢复 dataloader state_dict（`ray_trainer.py:1024-1025, 1105-1106` 已核实），数据顺序在续训后保持；优化器状态随 checkpoint 恢复。

### G5. verl 验证指标疑点：`val-aux/gsm8k/reward/mean@1` 恒等于 2.0
- **现象**：三个验证点该指标全部为 2.0，且与 `val-aux/num_turns/mean`（=2.0）完全相等。
- **矛盾**：自定义 reward 函数 `gsm8k_reward.py` 只返回 0/1（已核读源码），其均值不可能为 2.0；而 2.0 恰好是 num_turns 的均值。
- **推测**：verl 0.8 验证聚合层中 reward 类 aux 指标与 num_turns 指标存在串位/倍乘（例如 reward 被按 turn 数累计而非按样本平均），或 aux 指标标签错位。
- **建议**：源码审查 verl `val-aux` 聚合路径（reward_manager → val 输出字典的键名映射）；这也说明基准跑应至少人工抽查一次"指标 × 语义"对照表，而不是只看曲线形态。
